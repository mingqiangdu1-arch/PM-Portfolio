# 数据库详细设计

> 文档状态：当前有效
> 设计版本：V1.0
> 建立日期：2026-07-29
> 确认日期：2026-07-29
> 数据库：MySQL 8.4 LTS / InnoDB / utf8mb4
> 边界：本文件达到 DDL-ready，但不包含 SQL、Alembic、OpenAPI、JSON Schema 或业务代码

## 1. 设计结论

本设计从当前正式产品设计、已验收交互设计、页面状态机和 Development Planning 反向生成唯一数据模型。历史 `草稿4/6/7` 仅作为追溯输入，历史的 42 张概念表、41 张物理表及其中冲突关系不构成实施基线。

数据库按“全量设计、实施分期”处理：

- Sprint 0～5 只创建 MVP 主链、AI 追溯、事件、审计和指标验收所需表。
- Sprint 6 创建知识中心、知识使用和 Qdrant 索引登记表。
- 实验平台、自动清理作业等未来表只有在对应功能获批后创建，不提前建空表。
- 完整分析后台读取权威表、不可变事件和指标快照，不反向写业务状态。

## 2. 物理约定

### 2.1 类型与命名

| 项目 | 规则 |
|---|---|
| 表名、字段名 | 小写 `snake_case`，表名使用单数业务名 |
| 主键 | `id BIGINT UNSIGNED`，数据库内部使用；API 对外序列化为字符串 |
| 时间 | `DATETIME(6)`，统一保存 UTC；展示层转换时区 |
| 状态 | `VARCHAR(32)`；枚举由数据字典与应用契约共同约束 |
| 金额 | `DECIMAL(18,6)`，同时保存 `currency_code CHAR(3)` |
| 比率/得分 | `DECIMAL(10,6)`；原始分子、分母不得只保存比率 |
| 长文本 | `TEXT/MEDIUMTEXT/LONGTEXT` 按上限选择；敏感正文不复制到分析表 |
| JSON | 仅用于非核心扩展、快照或供应商原始映射；可过滤、关联、唯一或审计字段必须结构化 |
| 乐观锁 | 可变聚合根使用 `row_version BIGINT UNSIGNED NOT NULL DEFAULT 1` |
| 归档 | 可归档表使用 `archived_at`、`archived_by`；核心事实不物理删除 |
| 保留 | 分析/运行表使用 `retention_class`、`expires_at`；具体天数待安全与合规 Gate 冻结 |

默认公共字段组：

- `created_at DATETIME(6) NOT NULL`、`created_by BIGINT UNSIGNED NULL`。
- 可修改记录增加 `updated_at`、`updated_by`、`row_version`。
- 版本/提交/调用等不可变事实不更新原行；更正使用新版本、自关联或补偿记录。

### 2.2 外键与删除

- 实体外键默认 `ON DELETE RESTRICT`，防止删除父记录时丢失历史。
- 纯从属且没有独立审计价值的临时明细才允许级联删除；本设计的正式版本、事件、审计、调用、评价均不级联删除。
- `file_relation`、`behavior_event` 等多态引用无法使用数据库外键，必须通过应用校验、对象类型枚举、复合索引和数据质量查询保护。
- Qdrant 数据是派生索引，不参与 MySQL 外键，不成为事实源。

### 2.3 当前唯一性

MySQL 没有通用的部分唯一索引。以下“同组最多一个当前行”采用可空生成列加唯一索引实现，应用事务仍需锁定所属聚合根：

| 规则 | 生成列 | 唯一索引 |
|---|---|---|
| 一个 Project 只有一个工作版本 | `current_project_key = IF(is_working=1, project_id, NULL)` | `uk_project_one_working(current_project_key)` |
| 一个 Project Version 只有一个主 PRD | `main_prd_key = IF(is_main=1 AND archived_at IS NULL, project_version_id, NULL)` | `uk_version_one_main_prd(main_prd_key)` |
| 一个业务对象只有一个有效产物版本 | `effective_owner_key = IF(is_effective=1, owner_id, NULL)` | 各版本表独立唯一索引 |
| 一个 Plan 只有一个当前有效确认轮次 | `effective_plan_key = IF(is_effective=1, implementation_plan_id, NULL)` | `uk_plan_one_effective_round(effective_plan_key)` |
| 一个 Skill/Prompt/Template/Checklist 只有一个当前版本 | 对应 `current_owner_key` | 各版本表独立唯一索引 |
| 一个 PRD 只有一个当前 Flow 决策 | `current_prd_key = IF(is_current=1, prd_id, NULL)` | `uk_flow_one_current(current_prd_key)` |
| 一个 AI Result 只有一个初始 Adoption | `initial_result_key = IF(supersedes_adoption_id IS NULL, ai_result_id, NULL)` | `uk_adoption_initial(initial_result_key)` |

## 4. 核心模型

### 4.1 Project 与版本

- `project` 只保存项目身份、归档状态和最近访问模块，不把生命周期状态、工作流节点混为一个字段。
- `project_version` 保存迭代谱系、生命周期状态、当前工作流节点和工作版本标识。新项目的 V1 与 `project` 在同一事务创建。
- 查看历史版本不写 `is_working`；设置工作版本是独立命令与审计事实；回滚通过新建 `project_version` 完成。
- `version_change_record` 记录来源版本、目标版本、原因、来源 Issue 和继承摘要，不替代版本实体。

关键约束：

- `uk_project_version_no(project_id, version_no)`。
- `project_version.parent_version_id` 必须属于同一项目。
- 派生、设置工作版本均携带幂等键和 `expected_version`。
- `project.current_workflow_node` 不存在；节点只在 `project_version.workflow_node` 保存。

### 4.2 领域专属文档版本

Requirement、PRD、Flow、Implementation Plan、File、Template 和 Checklist 分别维护版本，不建立一个可任意混用的通用文档表。

所有版本表遵循：

- 唯一版本号：`(owner_id, version_no)`。
- `source_version_id` 保存派生来源；无来源时为空。
- `content_format`、`content_ref`/`content_json`、`content_hash` 明确内容位置和完整性。
- `status` 区分 draft、candidate、effective、superseded、archived。
- 正式版本不可原位修改；元数据更正不得改变正文哈希。
- `created_from_ai_result_id` 可空，用于连接 AI 候选。

特殊规则：

- `requirement_version` 保存原始输入、确认事实、遗留与风险接受结果；原始输入不被整理稿覆盖。
- `prd_version` 保存结构化 Tiptap JSON 和可选的渲染摘要；同一 Project Version 只能有一个有效主 PRD。
- `flow_version` 保存文本流程、Mermaid、`.drawio` 文件版本引用和逻辑校验结果；仅布局变化目前仍创建新候选版本。
- `flow_export` 只保存同一 Flow Version 的 PNG/SVG 派生物和哈希，不形成业务版本。
- `implementation_plan_version` 必须关联评审范围快照；AI 候选正式化后才成为有效版本。
- `file_version` 保存对象存储键、校验和、大小和 MIME；对象存储键不是业务 ID。

### 4.3 Review、确认与验证

- `design_review_scope` 将 Review 固定到一个或多个明确产物版本，避免评审过程看到漂移内容。
- `review_feedback` 保存问题本体；每次接受、拒绝、暂缓、澄清写入新的 `review_feedback_disposition`，不覆盖历史处理。
- `confirmation_round` 对所属 Plan 不可变；确认成功时在同一事务撤销旧 `is_effective` 并设置新轮次。
- `difference_record` 结构化保存原设计、实际情况、类型、原因、影响、阻断级别和处理结论。
- `readiness_check_result` 保存规则版本、检查项、结果和证据；不能只保存一个布尔值。
- `test_record` 提交后不可变；预留 `supersedes_test_record_id`，但更正流程未获产品确认前不得启用。
- `issue` 是统一主对象；`bug_detail`、`optimization_detail` 与 `issue` 1:0..1，且必须与 `issue.issue_type` 一致。
- `issue_disposition` 追加记录当前修正、派生版本、暂缓、拒绝及理由；派生目标在实际成功后关联目标版本。

### 4.4 AI 配置与执行

- `model_catalog` 仅描述供应商模型目录；`provider_profile` 保存 Base URL、运行参数和 Secret 引用，不保存明文密钥。
- Skill、Prompt、Template、Context Strategy 均版本化。`context_strategy_version.skill_version_id` 必填。
- `ai_task` 对应一次用户意图；重试通过 `retry_of_task_id` 形成新任务或在同一任务中新增调用，具体由重试语义决定。
- `ai_call` 对应一次供应商调用；每次重试新增行并保留失败事实。
- `ai_context_usage` 一行对应一个候选来源，记录是否检索、是否实际注入、来源版本、摘要/指纹和排除原因，不复制敏感正文。
- `ai_result` 保存候选元数据、内容引用/摘要、格式检查和目标快照；`ready` 不等于正式产物。
- `ai_evaluation` 分别保存自动检查、用户抽样、专家抽样，不互相覆盖，并绑定 `rubric_version`。
- `ai_adoption` 保存 adopted、adopted_after_edit、rejected、not_reviewed，修改强度和原因；一个已评审结果只有一个当前用户结论，更正通过新记录并引用前一记录。

### 4.5 事件、审计与指标

- `behavior_event` 是分析明细，不替代业务实体、审计或服务日志。
- `operation_audit_log` 保存谁在何时对哪个对象执行了什么关键命令、结果与 trace；不得保存密码、Token 或密钥。
- `business_event_outbox` 与业务事实同事务，`ai_event_outbox` 与 AI 运行事实同事务；两个表使用同一事件契约但写权限分离。消费者通过 `event_id` 幂等写入 `behavior_event`。
- `event_compensation` 指向被修正事件，说明修正类型和替代载荷；原事件不删除、不更新。
- `event_ingest_rejection` 保存 Schema 校验、引用失败和隐私规则拒收，不进入正式指标。
- `metric_definition` 保存公式口径与版本；`metric_snapshot` 保存分子、分母、值、样本量、过滤和数据质量状态。
- 指标计算失败不得回滚已成功业务动作；关键审计或 Outbox 写入失败则关键命令回滚。

### 4.6 知识与 Qdrant

- Experience Candidate 必须经人工审核后才能生成 `experience_version` 的有效版本。
- Checklist 采用 `checklist` + `checklist_version`；正文或适用范围变化必须新建版本。
- `knowledge_usage` 记录 retrieved、injected、cited、adopted 各阶段，并绑定 `ai_task_id`、`ai_call_id`、资产版本和实际排序。
- `knowledge_index_record` 只登记 Qdrant point、索引版本、来源哈希和重建状态；删除 Qdrant 索引不删除 MySQL 知识事实。
- Sprint 0～5 不部署 Qdrant；预置 Skill/Prompt/Template 的使用仍通过 AI 上下文记录追溯。

## 5. 服务写入责任

| 服务/角色 | 允许写入 | 禁止写入 |
|---|---|---|
| Business API | 身份、项目、业务产物、正式化、Review、确认、Test、Issue、文件元数据、审计、业务 Outbox | 供应商调用结果、Qdrant 索引 |
| AI Service/Worker | `ai_call`、`ai_context_usage`、`ai_result`、自动 `ai_evaluation`、AI Outbox；按任务契约更新 AI 运行状态 | Project Version、正式产物生效、Review/确认/Test/Issue 结论 |
| Event Consumer | `behavior_event`、`event_ingest_rejection`、消费游标 | 修改业务事实或审计事实 |
| Metric Job | `metric_snapshot`、`data_quality_run/issue`、`optimization_metric_result` | 修改原始事件、业务表或评价 |
| Analysis Backend | 只读权威表与事件；写报表导出作业元数据时另行建专属表 | 直接改变业务状态 |
| Qdrant Adapter（S6） | Qdrant 和 `knowledge_index_record` | 把向量结果写成正式知识 |

同一 MySQL 8.4 实例允许多个服务连接，但按表授权；跨服务关联使用版本化契约和 ID，不共享表写权限。

## 6. 索引策略

### 6.1 通用查询索引

- 所有外键列建立左前缀索引。
- 业务列表采用 `(parent_id, status, updated_at, id)` 或 `(parent_id, created_at, id)` 支持稳定游标。
- 事件采用 `(event_name, occurred_at, id)`、`(project_version_id, occurred_at, id)`、`(ai_task_id, occurred_at, id)`。
- AI 调用采用 `(ai_task_id, sequence_no)` 唯一索引及 `(provider_profile_id, status, started_at)` 诊断索引。
- 上下文采用 `(ai_call_id, was_injected, source_type)` 和 `(source_type, source_id, source_version_id)`。
- Issue 采用 `(project_version_id, status, priority, created_at, id)`；可选 Test 关联单独索引。
- 审计采用 `(object_type, object_id, occurred_at, id)`、`(actor_user_id, occurred_at, id)`、`trace_id`。

### 6.2 禁止的索引方式

- 不为低选择性的单独布尔列创建普通索引。
- 不为任意 JSON 路径预建索引；只有稳定查询条件才能转为生成列并索引。
- 不以 `updated_at` 单列支撑大表分页。
- 不把正文、Prompt、上下文摘要加入普通 B-Tree 索引。

### 6.3 容量与分区

MVP 不预设分区。`behavior_event`、`operation_audit_log`、`ai_call` 达到单表千万级或维护窗口不可接受时，再依据 `occurred_at/started_at` 做月分区评估。分区不能破坏唯一性、外键、补偿关系或查询血缘。

## 7. 事务与一致性

| 命令 | 同一事务必须完成 |
|---|---|
| 创建项目 | `project`、V1 `project_version`、项目 owner、审计、Outbox |
| 设置工作版本 | 锁定 Project、撤销旧工作版本、设置新版本、审计、Outbox |
| 派生版本 | 新版本、谱系、继承摘要、Issue 去向回填、审计、Outbox |
| 正式化 AI 候选 | 校验目标快照、创建产物版本、写 `ai_adoption`、审计、Outbox |
| 评审通过 | 锁定 Review、校验阻断项、写结论、审计、Outbox |
| 确认轮次生效 | 校验 Readiness、撤销旧有效轮次、设置新轮次、审计、Outbox |
| 提交 Test Record | 冻结事实、证据关联、审计、Outbox |
| Issue 去向 | 追加 disposition；派生成功后再关联目标版本；审计、Outbox |

模型调用、文件上传、对象存储写入和 Qdrant 操作不得持有 MySQL 长事务。对象存储写成功但元数据失败时登记孤儿清理候选，不返回业务成功。

## 8. 幂等、并发与补偿

- `idempotency_record` 以 `(user_id, endpoint_key, idempotency_key)` 唯一；保存请求摘要、状态、响应引用和到期时间。
- 同 Key 不同请求摘要返回冲突，不复用旧响应。
- 可变资源命令必须带 `expected_version`；冲突返回最新 `row_version` 和对象引用。
- 已成功的业务事实不因事件消费者或指标计算失败而回滚；Outbox 重试不生成新业务事实。
- 事件重复以 `event_id` 去重；业务自然键只作为数据质量辅助，不能替代事件 ID。
- 修正错误事件使用 `event_compensation`；修正不可变业务记录使用新版本或 `supersedes_*` 关系。

## 9. 隐私、安全与保留

- 事件和分析明细使用内部 `user_id`；`session_id` 使用不可逆匿名标识。
- 默认不采集 IP、完整 User-Agent、鼠标轨迹、页面正文、文件正文和剪贴板内容。
- Provider 密钥只保存 Secret Manager/部署 Secret 引用；禁止进入 JSON、日志、事件、错误响应和 Git。
- 未采用 AI 输出默认只保存摘要、指纹、检查结果和必要审计引用；正式产物正文按业务版本规则保存。
- `retention_policy` 定义数据分类、适用表、过期字段、清理方式、法律保留和审批状态。具体天数在生产前由安全/合规 Gate 冻结。
- 清理操作必须写 `data_purge_run`（未来启用）或等价审计；不得借清理覆盖业务版本历史。

## 10. 历史草案关系检查

| 历史对象/设计 | 处理 | 当前设计 |
|---|---|---|
| User 1:N Project | 保留并增强 | 增加 `project_member` 支持同一用户兼任项目角色；Project owner 仍明确 |
| Project.current_version_id + Project Version.is_current | 拆分 | 工作版本只在 `project_version.is_working` 表达；查看上下文不入库为当前版本 |
| Project.current_stage | 废弃混合字段 | `project_version.lifecycle_status`、`workflow_node`、`project.last_module` 分域 |
| Requirement 单表正文 | 拆分 | `requirement` + `requirement_version`，保留原始输入与确认版本 |
| PRD.content + PRD Version.content 双份正文 | 收敛 | `prd` 保存身份，正文只在 `prd_version` |
| Flow 直接属于 Project Version | 废弃 | Flow 直接属于 PRD，并通过 PRD 间接归属 Project Version |
| Flow Version 单一 content | 拆分 | 文本、Mermaid、draw.io 引用、校验结果结构化；Export 独立派生表 |
| Design Review 只关联 prd_id | 拆分 | Review 属于 Project Version，`design_review_scope` 固定多个产物版本 |
| Implementation Plan 1:1 Confirmation / `plan_id UNIQUE` | 废弃 | Plan 1:N `confirmation_round`，同一 Plan 只有一个当前有效轮次 |
| Test Record 直接归 Project Version | 废弃冗余 | Test Record 直接归 Confirmation Round，项目版本由关系推导 |
| Test Record 1:N Bug | 废弃 | Issue 是主对象，可选关联 Test Record；Bug/Optimization 是扩展 |
| Optimization 与 Issue 并列 | 合并 | `optimization_detail` 必须依附 Issue；版本去向使用 `issue_disposition` |
| Checklist 无版本 | 补充 | `checklist` + `checklist_version` |
| Context Strategy 绑定 Skill | 修正 | Context Strategy Version 必须绑定 Skill Version |
| AI Call Record 单表 | 拆分 | Task、Call、Context、Result、Evaluation、Adoption 六类事实 |
| Operation Log 同时承担埋点 | 拆分 | `operation_audit_log` 与 `behavior_event` 分离 |
| api_config/model_config 保存密钥 JSON | 禁止 | 只保存 Provider Profile 与 Secret 引用 |
| MySQL vector_embedding 保存向量 | 废弃为事实表 | Sprint 6 使用 Qdrant；MySQL 只登记可重建索引映射 |
| File Relation 使用 file_id | 修正 | 关联 `file_version_id`，确保历史使用的文件版本可追溯 |
| 物理删除或覆盖历史 | 禁止 | 归档、新版本、补偿和不可变事实 |

## 11. 迁移批次

| 批次 | 内容 | Gate |
|---|---|---|
| M0 Foundation | 身份最小表、AI 配置版本、事件/审计/Outbox/幂等、Schema 元数据 | 空库迁移、重复迁移、约束测试 |
| M1 Project/File | Project、Version、Context、角色、文件元数据与版本 | 创建 V1、工作版本唯一、文件失败恢复 |
| M2 Requirement/AI | Requirement 版本、AI Task/Call/Context/Result/Evaluation/Adoption | 正式结果追溯完整率 100% |
| M3 PRD/Flow | PRD 版本；Flow Gate 通过时才创建 Flow 三表 | 主 PRD 唯一、Flow 关闭无空壳事实 |
| M4 Review/Confirmation | Review 快照、反馈处置、Plan 版本、Round、Difference、Readiness | 阻断门禁与唯一有效轮次 |
| M5 Validation/Data | Test、Issue、去向、指标定义/快照、质量检查、优化评价 | T01～T07、指标血缘与数据质量 |
| M6 Knowledge | Experience/Checklist 版本、Knowledge Usage、Qdrant 索引登记 | 人工审核、可重建、降级 |
| MF Future | 实验分流和清理作业 | 独立产品/安全审批 |

每批迁移需验证空库、上一版本升级、失败重试、锁风险、空间预检和迁移后一致性查询。业务回滚不删除历史事实；数据库迁移回退只能恢复兼容结构或使用前向修复。

## 12. DDL-ready 验收

- 表清单、字段、类型、主外键、唯一约束和索引均能在《数据字典》中定位。
- ER 与表清单不存在孤儿实体或反向基数冲突。
- 当前工作版本、主 PRD、有效产物版本、有效确认轮次和当前配置版本均有数据库级唯一保护。
- 历史草案的冲突关系全部有保留、修正或废弃结论。
- MVP、Sprint 6、Future 表边界明确，未来表不进入 MVP 初始迁移。
- 不含明文凭据、无限制敏感正文复制或依赖 Qdrant 的业务事实。
