# 版本优化指标

> 文档状态：当前有效  
> 基线版本：V1.0  
> 生效日期：2026-07-27  
> 适用范围：产品发布、项目版本与 AI 能力版本的优化归因和前后验证

## 1. 设计目标

版本优化评价用于回答：某项明确变更是否改善了预期指标，同时没有损害质量、稳定性、时延、成本或流程完成。它不等于简单比较 V1 和 V2 的总量，也不允许把同期多项变化全部归因给单一优化。

## 2. 三类版本分别评价

| 版本类型 | 评价对象 | 典型变更 | 主要比较单元 |
|---|---|---|---|
| 产品发布版本 | 平台功能与流程 | 功能、门禁、交互或流程规则 | 同 cohort 项目版本/用户任务 |
| Project Version | 一轮产品迭代结果 | 需求、设计、实现和验证变化 | 同一项目的父子版本 |
| AI Capability Version | Skill、Prompt、Template、Context Strategy、Model 配置 | AI 执行和输出变化 | 同任务类型、同输入或可比任务 |

比较记录必须同时保存受影响的版本类型，禁止使用含糊的 `version=V2`。

## 3. 优化记录

每项优化必须在发布前建立 `optimization_id`，至少包含：

- 问题陈述和证据。
- 优化假设：对哪类用户/任务，什么变更预期改善哪个结果。
- 变更对象及变更前后版本 ID。
- 一个主指标、1～2 个驱动指标、1～2 个护栏指标。
- 对比方法、纳入/排除条件、基线窗、观察窗和最小样本要求。
- 同期变更、风险、负责人和预定复核时间。
- 结论：改善、无明显变化、恶化或证据不足。

## 4. 指标选择

### 4.1 产品流程优化

- 主指标：薄闭环完成率、目标阶段通过率或目标阶段周期。
- 驱动：阶段到达率、返轮率、阻断反馈/差异率。
- 护栏：Issue 密度、AI 重大错误率、P95 时延、用户放弃率。

### 4.2 AI 能力优化

- 主指标：有效采用率、直接采用率或目标质量维度。
- 驱动：完整度、大改率、拒绝原因分布、首次成功率。
- 护栏：重大错误率、调用成功率、P95 时延、Token/成本。

### 4.3 知识优化

- 主指标：引用后的有效采用率或目标质量维度变化。
- 驱动：检索命中、注入、引用和审核通过。
- 护栏：错误引用率、陈旧知识命中、时延和 Token。

每项优化只设一个主指标，防止事后挑选最有利的结果。

## 5. 对比方法

优先级从高到低：

1. 同一输入离线成对评测：适合 Prompt、Skill、Template 或模型版本；输入和上下文快照固定。
2. 同期受控分流：适合流量充足且风险可控的线上版本；随机分组并保留回退。
3. 分阶段灰度：比较同类用户/任务在相邻时间窗的表现，控制渠道、任务类型和复杂度。
4. 发布前后观察：仅在无法受控比较时使用，必须披露同期变化和归因限制。
5. 父子 Project Version 对比：用于同一项目迭代，报告结果变化，但不外推为平台普遍效果。

## 6. 可比性规则

- 任务类型、项目阶段、复杂度、输入完整度和上下文可用性应相同或分层。
- 指标公式、`metric_version`、评价量表和过滤条件保持一致。
- 基线窗与观察窗尽量覆盖相同工作日结构，排除故障和内部压测。
- 观察窗内若模型、Prompt、Skill、流程同时变化，标记为“组合变更”，不得归因给单项。
- 展示分子、分母、绝对差、相对差和样本量。
- 样本不足、数据质量不达标或分组严重失衡时，结论只能是“证据不足”。

## 7. 计算口径

| ID | 指标 | 公式/规则 | 用途 |
|---|---|---|---|
| VO-01 | 已归因优化数 | 具备完整优化记录的去重 `optimization_id` | 检查优化是否可评估 |
| VO-02 | 可比优化率 | 满足可比性要求的优化 / 已进入评估优化 | 评估证据质量 |
| VO-03 | 绝对变化 | `after - before` | 直接表达百分点或时长变化 |
| VO-04 | 相对变化 | `(after - before) / before`；before 为 0 时不计算 | 表达相对幅度 |
| VO-05 | 护栏恶化数 | 超过预先约定容忍区间的护栏数量 | 防止局部优化 |
| VO-06 | 版本改善率 | 主指标改善且护栏未恶化的优化 / 已完成评估优化 | 版本组合 KPI |
| VO-07 | 不确定率 | 证据不足优化 / 已评估优化 | 暴露决策风险 |
| VO-08 | 生效周期 | 发布至达到评估条件的时长 | 规划验证节奏 |
| VO-09 | 回退率 | 因主指标或护栏恶化回退的优化 / 已发布优化 | 检查发布质量 |

## 8. 结论规则

| 结论 | 条件 | 动作 |
|---|---|---|
| 改善 | 主指标达到预设最小改善幅度，护栏均在容忍区间，数据质量通过 | 保留版本并记录结论 |
| 无明显变化 | 数据充分但主指标未达到最小改善幅度，护栏稳定 | 停止扩大或提出新假设 |
| 恶化 | 主指标恶化或任一关键护栏越界 | 回退、降级或修复 |
| 证据不足 | 样本不足、数据质量失败、口径变化或多重混杂 | 延长观察或重新设计比较 |

“显著”和“容忍区间”必须在观察前定义。MVP 无历史基线时，先用绝对差和置信区间/样本说明，不强行宣称因果显著。

## 9. MVP 版本验证要求

### 9.1 必采

- 产品发布版本、Project Version、AI 能力版本 ID 及生效时间。
- 优化记录、影响任务/模块、主指标、驱动指标、护栏和观察窗。
- 每个 AI 任务实际使用的能力版本组合。
- 前后样本的任务类型、项目阶段、结果、采用状态和质量标签。
- 同期变更、异常窗口和排除原因。

### 9.2 最小执行方式

MVP 不要求自动实验平台。允许使用版本标签 + 固定查询/离线报表完成比较，但必须保证：可定位样本、公式一致、前后版本明确、结论可复核。对 Prompt/Skill 变更优先保留一组固定代表性任务做离线回归集。

### 9.3 发布门禁

- 无 `optimization_id` 和指标方案的变更可以发布，但不得宣称“数据验证有效”。
- 关键 AI 能力变更必须通过结构、安全和重大错误回归检查。
- 若调用成功率、重大错误率或 P95 时延超过预设护栏，停止扩大使用并进入回退评估。

## 10. MVP 基线与目标

1. 首次上线后采集 2～4 周稳定数据，形成任务类型和模块分层基线。
2. 基线至少包括薄闭环完成率、AI 有效采用率、直接采用率、大改率、重大错误率、任务成功率和 P95 时延。
3. 第一个优化周期再根据基线设定最小改善幅度和护栏容忍区间。
4. 目标必须说明依据、样本、适用范围和信心等级；不得复制外部 Benchmark 作为内部承诺。

## 12. 阶段验收

- 产品、项目和 AI 能力版本能够分别归因。
- 每项正式优化都有预先定义的主指标和护栏。
- 前后比较保留同口径、样本和排除条件。
- 版本结论支持“证据不足”，不把同期相关性包装为因果。
- MVP 能用基础记录完成至少一次可复核的前后版本比较。
