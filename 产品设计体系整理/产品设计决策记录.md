# 产品设计决策记录

> 文档状态：当前有效  
> 基线版本：V1.0  
> 建立日期：2026-07-27  
> 用途：记录跨文档冲突的裁决、理由、影响和后续验证项

## 1. 决策规则

- 状态分为：`已决定`、`暂定`、`待决定`、`已替代`。
- “已决定”可进入当前产品基线；“暂定”可用于下一阶段设计验证，但不能直接冻结为数据库/API 实现。
- 新决策不能删除旧记录；应新增记录并通过“替代关系”串联。
- 产品层决策不等于技术实现决策。ER、DDL、OpenAPI 和安全方案需在 Development Planning 阶段另行形成技术基线。

## 3. 详细决策

### PD-001 正式产品名称

- **状态**：已决定
- **决定**：正式名称为“AI 产品设计与验证平台”；“AI 产品工作流平台”“AI 产品工作平台”作为历史别名。
- **理由**：正式名称同时体现产品设计、实现对齐和真实验证，比“工作流”更准确描述核心价值。
- **影响**：新文档、导航标题和后续产品叙述使用正式名称；历史文件不改名。

### PD-002 用户角色边界

- **状态**：已决定
- **决定**：MVP 以产品负责人为核心用户和最终确认人；评审者、实现确认人、测试人员是流程参与身份，同一用户可兼任；复杂 RBAC 延后。
- **理由**：既有资料明确产品经理是核心用户，但没有足够证据支持复杂组织权限模型。先以责任边界完成闭环，避免提前扩大范围。
- **影响**：交互阶段要支持“由谁提交/确认”的身份记录，但不要求独立角色门户。

### PD-003 模块与导航命名

- **状态**：已决定
- **决定**：用户可见业务一级模块为项目中心、产品设计、实现确认、产品验证、知识中心、系统设置。AI、文件、上下文和审计是支撑能力；分析与运营后置。
- **理由**：“知识中心”能够覆盖 Experience、Checklist、Skill 和 Template；“数据中心”容易与指标分析混淆；AI Context Manager 本就被定义为隐藏后台能力。
- **影响**：后续信息架构使用该导航，不再沿用“数据中心/AI 能力中心”并列结构。

### PD-004 Issue、Bug、Optimization 模型

- **状态**：已决定
- **决定**：Issue 是统一主对象，记录来源、类型、影响和状态；Bug 与 Optimization 只保存类型特有字段。Issue 必须属于 Project Version，可选关联 Test Record。
- **理由**：问题也可能来自用户反馈或运行数据，不能强制属于测试；统一主对象能保持查询、流转和统计一致。
- **影响**：旧的 `Test Record 1:N Bug` 和 Issue/Bug/Optimization 并列口径废弃。具体扩展表还是单表 JSON 在数据库基线阶段决定。

### PD-005 实现确认基数

- **状态**：已决定
- **决定**：Implementation Plan 1:N Confirmation Round；每轮不可变，同一方案只有一个当前有效轮次。
- **理由**：实际实现可能多次提交和复核，覆盖单条记录会失去证据链。
- **影响**：旧的 `plan_id UNIQUE` 物理草案不可直接采用；测试记录指向具体轮次。

### PD-006 版本切换与回滚

- **状态**：已决定
- **决定**：查看历史版本不改变业务状态；设置当前工作版本是受审计操作；业务回滚通过基于历史版本派生新版本实现。
- **理由**：三种行为的风险与语义不同，不能由一个 `switch` 动作混合表达。
- **影响**：原 `/project/version/switch` 仅作为历史 API 草案，不进入当前契约。

### PD-007 数据库草稿效力

- **状态**：已决定
- **决定**：42 张概念表、41 张物理表及未落地关系对象均为历史设计输入，不构成开发基线。
- **理由**：表数量、关系、索引、外键和敏感配置尚未收敛，直接实现会固化冲突。
- **影响**：Development Planning 必须从当前产品对象关系生成唯一 ER、数据字典和可执行迁移；本阶段不裁定物理表数量。

### PD-008 三类阶段信息

- **状态**：已决定
- **决定**：Project Version 生命周期状态、工作流节点、最近访问模块分别建模。
- **理由**：三者变化频率、业务含义和使用者不同。
- **影响**：后续状态机和页面导航分别设计映射，不能复用 `current_stage` 单字段承载全部语义。

### PD-009 Flow 归属

- **状态**：已决定
- **决定**：Flow 直接属于 PRD，一个 PRD 可有多个 Flow；通过 PRD 间接归属 Project Version。Flow 为可选产物，跳过需记录原因。
- **理由**：现有物理草案已有 `prd_id`，且 Flow 表达特定产品设计内容；跨 PRD 总览 Flow 暂无核心场景证据。
- **影响**：版本级跨 PRD Flow 进入未来评估，不在 MVP 数据模型中预设。

### PD-010 Test Record 归属

- **状态**：已决定
- **决定**：Test Record 直接关联执行测试时的 Confirmation Round，通过该关系查询 Implementation Plan 和 Project Version。
- **理由**：验证必须对应明确实现证据；重复保存多个直接外键容易不一致。
- **影响**：若未来出现不依赖实现确认的研究性测试，应新增独立测试类型，而不是让核心归属变得含糊。

### PD-011 Context Strategy 版本绑定

- **状态**：已决定
- **决定**：Context Strategy 绑定 Skill Version，与 Prompt Version 一同记录于 AI Call。
- **理由**：Skill 版本变化可能改变必需上下文、优先级和压缩方式，只有版本级绑定才能复现。
- **影响**：旧的仅绑定 `skill_id` 设计被替代。

### PD-012 Checklist 版本化

- **状态**：已决定
- **决定**：采用 Checklist + Checklist Version；正文或适用场景变化生成新版本。
- **理由**：Checklist 会影响评审结果，必须保留历史调用口径。
- **影响**：State Machine 与数据库设计阶段只需补充元数据原位修改边界和版本状态枚举，不再重新讨论是否需要版本化。

### PD-013 MVP 闭环

- **状态**：已决定
- **决定**：MVP 必须以最薄实现跑通 Project Version → Requirement → PRD → Review → Plan → Confirmation → Test → Issue → 新版本派生。Flow 可选，知识与数据分析属于增强能力。
- **理由**：仅完成需求、PRD 和 Review 不能验证“设计与验证平台”的核心价值。原开发交接文档的第一至第三阶段解释为 MVP 内部交付里程碑，第四阶段为增强版本。
- **影响**：MVP 验收以端到端闭环为准；实现可分批，但不能把第一批功能宣称为完整 MVP。

### PD-014 API 风格

- **状态**：暂定
- **决定**：常规增删改查采用资源式 API；评审提交、确认、派生版本等具有明确业务含义的动作使用显式命令端点；AI 领域端点由通用异步任务能力承载。
- **理由**：纯动作式路径难以形成一致契约，但强行把所有业务命令伪装成 CRUD 也会损失语义。
- **待验证**：Development Planning 阶段补齐鉴权、幂等、并发控制、分页、错误码、上传和异步任务协议。

### PD-015 模型目录与连接配置

- **状态**：已决定
- **决定**：平台模型目录保存供应商、模型标识和能力元数据；运行连接配置保存用户/平台的供应商连接与安全凭证引用，两者分离。
- **理由**：模型能力信息与密钥的生命周期、安全级别和复用范围不同，混入一个 `model_config` 会导致审计与权限不清。
- **影响**：AI Call 引用模型目录标识和实际运行配置版本；密钥不得以普通 JSON 明文保存。具体 Secret 方案留待安全设计。

### PD-016 Flow 分层生成、评审与交付路径

- **状态**：暂定
- **决定**：主流程图按“PRD/需求文档 → 选择范围与类型 → AI 提取 → 文本流程 Review → Mermaid Review → `.drawio` → 布局优化/可选人工微调 → 逻辑校验与版本保存 → `.drawio`、PNG、SVG 交付”推进。子流程从主流程的节点或业务模块进入，定位来源文档并接受用户补充要求，经文本和 Mermaid Review 后保存为独立 Flow。
- **理由**：先审文本可以低成本纠正业务语义，Mermaid 适合在生成可编辑图文件前确认结构；`.drawio` 保留后续编辑能力，PNG/SVG 提供稳定的查看和交付格式。
- **边界**：Flow 仍为 PRD 下的可选产物；子流程是独立 Flow，但必须保留父 Flow、来源节点/模块和来源文档版本关系。AI 生成及布局结果不得绕过用户 Review 自动成为正式设计。
- **待验证**：流程图类型与生成范围枚举、Review 交互及确认语义、Mermaid 到 `.drawio` 的转换保真度、自动布局能力、逻辑校验规则、仅布局变化时的版本策略，以及 PNG/SVG 导出规格。

### PD-017 MVP 最小数据闭环

- **状态**：已决定
- **决定**：MVP 开发必须同步记录核心业务事实、AI 调用追溯、输出质量检查、用户采用/修改/拒绝结论和版本归因，使核心功能可统计、AI 输出可评价、版本优化可比较。完整埋点平台、自动评测、知识运营指标和分析看板仍属于增强能力。
- **理由**：若等到增强阶段才采集，MVP 上线后将无法建立可信基线，也无法复盘 AI 与流程优化；但提前建设完整分析产品会扩大 MVP 范围。
- **影响**：产品层指标口径由四份数据设计文档定义；事件字段、状态映射、存储和计算实现分别在状态机与 Development Planning 阶段冻结。未获得稳定基线前不设置缺少证据的业务目标值。

## 4. 尚未进入产品基线的事项

以下事项不能从现有草稿安全推断，留待后续阶段：

- 组织、租户、项目成员与细粒度权限矩阵。
- Project Version、Review、Confirmation、Issue 等完整状态机。
- 唯一 ER、物理表数量、外键/删除/归档策略和索引。
- 字段级 OpenAPI 契约与异步任务协议。
- 字段级事件契约、状态机到事件的精确映射、物理存储、数据保留期限与可执行数据血缘；产品层指标口径已由四份数据设计文档建立。
- 具体模型供应商、向量数据库和部署规模选择。
