# 版本管理规则

> 文档状态：当前有效  
> 基线版本：V1.0  
> 生效日期：2026-07-27  
> 适用范围：项目版本、产物版本、确认轮次、AI 能力版本与设计文档状态

## 1. 版本对象

平台存在五类不可混用的版本对象：

| 对象 | 表达内容 | 何时新建 |
|---|---|---|
| Project Version | 一轮完整产品迭代 | 产品或验收口径发生实质变化 |
| Artifact Version | PRD、Flow、Plan 等内容修订 | 正式内容被修改并保存 |
| Confirmation Round | 一次实现确认事实 | 重新提交实现证据或重新确认 |
| AI Capability Version | Skill、Prompt、Template、Context Strategy | 影响执行或输出的配置变化 |
| Product Design Baseline | 当前有效产品设计文档集合 | 跨模块产品口径批准变更 |

文件自身版本是存储层版本，不自动等同于业务产物版本。

## 2. Project Version 规则

### 2.1 创建条件

必须创建新版本：

- 新功能或明确的新业务需求。
- 业务规则、用户范围、产品方向或验收标准变化。
- 大范围体验优化或重大实现调整。
- 基于历史版本进行业务回滚。

不创建新版本：

- 文案和纯展示修正。
- 不改变业务规则的普通缺陷修复。
- 小范围异常处理和数据修复。

边界不清时，由产品负责人记录判定依据；宁可显式派生，不允许静默改变已完成版本的业务含义。

### 2.2 创建与继承

- 新项目自动创建 V1。
- 新版本记录 `parent_version_id` 和 `derived_reason`。
- 默认继承项目背景、已确认长期上下文和主 PRD 的副本引用。
- Requirement 可从来源 Issue/Optimization 生成新记录。
- Flow、Implementation Plan、Confirmation Round、Test Record 不默认继承。
- 继承不代表继续共享可变记录；新版本形成独立业务事实。

### 2.3 切换、当前工作版本与回滚

- **查看切换**：仅改变用户正在查看的版本，不改项目业务状态。
- **设置当前工作版本**：改变项目默认进入版本，需要权限、审计和并发校验。
- **业务回滚**：不恢复并覆盖旧记录，而是基于目标历史版本创建一个新版本。

禁止使用含糊的 `version/switch` 同时承担三种语义。API 应分别表达读取上下文、设置当前版本和派生版本。

## 3. 产物版本规则

- 每个 PRD、Flow、Implementation Plan 同一时刻只有一个当前有效版本。
- 已提交评审的产物版本冻结；修改产生新版本，不改变原评审证据。
- 版本至少记录：版本号、变更摘要、创建人、创建时间、来源版本和状态。
- 小修改也不能覆盖已评审或已确认的内容。
- 草稿可在未提交前保存增量，但发布为新正式版本时必须生成变更摘要。

建议状态：`draft → in_review → effective → superseded → archived`。被替代版本仍可查看和引用。

### 3.1 Flow 版本与交付物（暂定）

- 一个 Flow Version 对应同一版业务逻辑的文本流程、Mermaid 表达和 `.drawio` 可编辑源；三者必须能够相互追溯。
- `.drawio` 是可编辑交付源，PNG 和 SVG 是由同一 Flow Version 导出的交付文件，不建立独立业务版本。
- 文本流程 Review 与 Mermaid Review 必须引用明确的 Flow Version 或候选版本；评审通过后的逻辑修改必须创建新版本。
- `.drawio` 生成、自动布局或人工微调完成后，需通过逻辑校验才能成为当前有效版本。
- 子流程保存为独立 Flow，并记录父 Flow、来源节点或业务模块及来源 PRD/Requirement Version；父流程更新不自动覆盖子流程。
- 仅改变视觉布局、不改变业务逻辑时是否生成新 Flow Version，留待交互设计与状态机阶段确定；在规则冻结前不得覆盖已评审版本。

## 4. 确认轮次规则

- Implementation Plan 与 Confirmation Round 为 1:N。
- 每轮确认是不可变事实，记录提交证据、差异、确认人、时间和结论。
- 同一方案最多一个“当前有效确认轮次”；新轮次生效后，旧轮次标记为 `superseded`。
- 实现变化、阻断差异修复或已确认设计更新后，必须创建新确认轮次。
- Test Record 直接关联执行验证时的确认轮次，保证验证证据可复现。

## 5. AI 能力版本规则

- Prompt 绑定 Skill Version，不只绑定 Skill。
- Context Strategy 绑定 Skill Version，或自身版本明确记录生效区间；MVP 统一采用前者。
- 正式 AI 结果记录 Skill Version、Prompt Version、Template Version、Model 标识及上下文来源。
- 模型供应商参数和用户凭证配置属于运行配置，不替代平台模型目录版本。
- 已产生正式结果的版本不可删除，只能停用或废弃。

## 6. Checklist 与知识版本规则

- Experience 重要内容修订产生新版本或新的有效记录，不覆盖历史引用。
- Checklist 采用 Checklist + Checklist Version；正文、适用场景或判定提示变化时创建新版本。
- 标签修正等不影响含义的元数据调整可原位更新，但需保留操作审计。
- 候选、正式、停用和废弃是生命周期状态，不是内容版本号。

## 7. 产品设计文档状态

### 7.1 状态定义

| 状态 | 含义 | 能否作为实现依据 |
|---|---|---|
| 草稿 | 未完成或未经评审 | 否 |
| 待评审 | 内容完整，等待确认 | 否 |
| 当前有效 | 已批准的唯一当前口径 | 是 |
| 历史设计 | 曾有参考价值，已被新基线替代 | 否，仅追溯 |
| 废弃设计 | 已明确否决或不再适用 | 否 |
| 无效文件 | 空文件、损坏文件或误同步占位 | 否 |

**历史设计来源**

- `项目初始化/` 下的分析与规划文档：阶段分析证据，不是产品设计定义。

**无效文件**

- `数据埋点与数据库设计方案.docx`：0 字节占位。
- `项目开发规划与MVP路线.docx`：0 字节占位。

**已废弃口径（不等于删除源文件）**

- 用“数据中心”或独立“AI 能力中心”作为当前一级导航。
- 把 Issue、Bug、Optimization 作为并列主对象。
- 一个 Implementation Plan 只能有一条可覆盖的确认记录。
- 用版本切换直接覆盖历史完成版本。
- 把工作流节点、版本状态和最近模块存入同一枚举。

## 8. 变更流程

1. 提交变更建议，说明问题、影响模块和证据。
2. 在《产品设计决策记录》中新增拟议决策。
3. 更新唯一领域主责文档，并标注新基线版本。
4. 检查功能架构、核心流程、MVP 范围和术语的一致性。
5. 批准后将旧版本标记为历史设计，更新 `PROJECT_MEMORY.md` 和 `PROJECT_STATUS.md`。
6. 实现与验收只能引用批准后的当前有效版本。

禁止只修改汇总文档、不更新主责文档；禁止把未决建议描述为已确认事实。
