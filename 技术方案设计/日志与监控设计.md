# 日志与监控设计

> 文档状态：当前有效
> 基线版本：V1.0
> 生效日期：2026-07-29
> 建立日期：2026-07-29
> MVP 方案：结构化 JSON 日志 + Loki + Prometheus + Alertmanager + Grafana；不部署 Tempo

## 1. 设计结论

日志、指标、审计、业务事件和 AI 追溯相互独立：

- 日志用于运行诊断，可轮转、可有限保留。
- 指标用于健康、性能、容量和告警。
- `operation_audit_log` 用于关键操作证据，不能被日志替代。
- `behavior_event` 用于分析，不能用于恢复业务状态。
- AI Task/Call/Context/Result 是可复现追溯事实。

MVP 不部署 Tempo；跨服务通过 `trace_id`、`command_id`、`task_id` 在 Loki 和 MySQL 事实之间关联。应用仍保留 OpenTelemetry 兼容的 trace context 传播边界，后续增加 Trace Backend 不改业务契约。

## 2. 组件

| 组件 | 责任 | 持久化 |
|---|---|---|
| 应用 Logger | JSON stdout、去敏、关联字段 | Docker 日志短期缓冲 |
| 日志采集 Agent | 采集容器 stdout、补充 service/env/release | 无权读取业务正文 |
| Loki | 日志索引与查询 | 独立卷 |
| Prometheus | 抓取服务/Exporter 指标 | 独立卷 |
| Alertmanager | 聚合、抑制、路由告警 | 配置与状态 |
| Grafana | Dashboard、日志跳转、告警视图 | 独立卷 |

## 3. 结构化日志 Schema

每条应用日志至少包含：

| 字段 | 必需 | 说明 |
|---|---:|---|
| `timestamp` | 是 | UTC RFC 3339，微秒可得时保留 |
| `level` | 是 | debug/info/warn/error/critical |
| `service` | 是 | web/business-api/ai-api/ai-worker/event-consumer/metric-job |
| `environment` | 是 | local/ci/staging/production |
| `product_release` | 是 | 发布版本 |
| `logger` | 是 | 模块名 |
| `event` | 是 | 稳定机器事件名 |
| `message` | 是 | 去敏的人类摘要 |
| `trace_id` | 请求链必需 | 跨请求关联 |
| `request_id` | HTTP 必需 | 单次请求 |
| `command_id` | 写命令必需 | 幂等/因果 |
| `task_id` | AI/后台任务必需 | public task id |
| `call_id` | Provider 调用时 | AI Call |
| `user_id` | 有身份时 | 内部 ID；禁止邮箱 |
| `project_id` | 项目作用域时 | 字符串化 ID |
| `object_type/id` | 对象操作时 | 不含正文 |
| `duration_ms` | 完成日志 | 非负 |
| `result_status` | 完成日志 | success/failed/partial/cancelled/blocked |
| `error_code` | 失败时 | 统一分类 |
| `retryable` | 失败时 | boolean |

不得把高基数或敏感字段设为 Loki Label；Label 仅使用 environment、service、level、product_release。

## 4. 禁止记录

- 密码、JWT、Refresh Token、Provider/API Key、DB/S3/Redis Secret。
- 完整 Authorization/Cookie/Header。
- 签名上传/下载 URL、对象存储键。
- 完整 Prompt、Context、文件正文、PRD/Plan 正文、未采用 AI 结果全文。
- 原始供应商请求/响应全文。
- 默认 IP、完整 User-Agent、鼠标轨迹、剪贴板内容。
- SQL 参数中的敏感正文或数据库连接串密码。

可记录内容哈希、长度、Token 数、字段数量、去敏摘要、供应商 request ID 和稳定错误分类。

## 5. Trace 与因果传播

### 5.1 HTTP

- 入口接受合法 `X-Request-ID`，服务端生成/传播 `trace_id`。
- Business API 调用 AI API 时传播 `trace_id`、新内部 `request_id`、原 `command_id`。
- 响应 Header 与响应体返回同一 `trace_id`。

### 5.2 Celery

消息 Header 包含 `trace_id,command_id,task_public_id,correlation_id,causation_id,product_release`；消息正文只放最小路由数据。

Worker 每个阶段创建结构化开始/完成日志，不把每个流式 Token 写日志。

### 5.3 Outbox 与事件

Business/AI Outbox、行为事件、审计记录沿用同一 `trace_id/command_id`。消费者生成自己的 `request_id`，保留 correlation/causation。

## 6. 日志级别

| Level | 使用 |
|---|---|
| DEBUG | Local/受控短期开启；Schema/路由摘要，不含正文 |
| INFO | 请求完成、状态转换、发布、任务阶段、备份结果 |
| WARN | 可恢复依赖错误、重试、慢请求、接近容量、权限变化 |
| ERROR | 请求确定失败、任务失败、Outbox/事件拒收、备份失败 |
| CRITICAL | 数据不可恢复风险、迁移破坏、Secret 暴露疑似、核心事实写入不一致 |

预期的 4xx 不统一记录 ERROR；401/403、409、422 以 info/warn 并通过指标统计，避免告警噪声。

## 7. 指标目录

### 7.1 Web/API

- `http_requests_total{service,route,method,status_class}`
- `http_request_duration_seconds` histogram
- `http_inflight_requests`
- `sse_connections`、`sse_disconnects_total`、`sse_delivery_lag_seconds`
- `auth_login_failures_total{reason}`、`refresh_reuse_detected_total`
- `idempotency_conflicts_total{route}`
- `version_conflicts_total{object_type}`

Route 使用模板路径，不使用实际 ID。

### 7.2 AI/Worker

- `ai_tasks_total{task_type,status}`
- `ai_task_duration_seconds{task_type}`
- `ai_queue_depth{queue}`、`ai_oldest_queued_seconds{queue}`
- `ai_worker_active`、`ai_worker_heartbeat_age_seconds`
- `ai_calls_total{provider,model,status,error_class}`
- `ai_call_duration_seconds{provider,model}`
- `ai_tokens_total{provider,model,direction}`
- `ai_retries_total{reason}`、`ai_cancel_latency_seconds`
- `ai_traceability_incomplete_total`
- `ai_stale_target_total{task_type}`

不得把 task ID、user ID、project ID 或 capability fingerprint 用作 Prometheus Label。

### 7.3 数据/事件

- `outbox_pending_total{producer}`、`outbox_oldest_pending_seconds`
- `event_ingest_total{event_name,status}`
- `event_schema_rejections_total{producer,event_name,code}`
- `event_duplicates_total{producer}`
- `data_quality_issues_total{severity,rule_id}`
- `metric_job_duration_seconds`、`metric_job_failures_total`
- `formalized_ai_traceability_ratio`

### 7.4 基础设施

- MySQL up、连接、慢查询、锁等待、磁盘、备份时长。
- Redis up、内存、eviction、连接、broker 队列、持久化最后成功。
- MinIO up、容量、对象操作错误、签名请求失败。
- 容器 CPU/内存/重启、宿主机磁盘/inode/负载。
- Loki/Prometheus 自身容量、采集丢弃和查询失败。

## 8. SLI 与告警

| 告警 | 触发候选 | 严重度 | Owner | 首要动作 |
|---|---|---|---|---|
| API 高错误率 | 5 分钟 5xx >2% 且请求量达最小样本 | P1 | 后端 | 按 release/route 定位 |
| API 延迟 | 非 AI P95 >500ms 持续 10 分钟 | P2/P1 | 后端 | 慢查询/依赖分析 |
| AI 队列积压 | 最老 interactive >120s 或持续增长 | P1 | AI/数据 | 限流、检查 Worker/Provider |
| Worker 丢失 | heartbeat 超过 60s | P1 | AI/数据 | 停止新任务、恢复 Worker |
| Provider 失败 | 5 分钟失败率 >20% 且样本≥10 | P1 | AI/数据 | 熔断、转人工路径 |
| 追溯不完整 | 正式结果完整率 <100% | P0 | AI/数据+后端 | 阻止正式化/发布 |
| Redis 不可用 | ping 失败 1 分钟 | P1 | 后端 | 拒绝新 AI、保留 CRUD |
| MySQL 不可用 | ready 查询失败 | P0 | 后端 | 维护模式、禁止写 |
| MinIO 不可用 | ready/对象错误持续 | P1 | 后端 | 禁止上传、保留元数据 |
| Outbox 积压 | 最老 pending >5 分钟 | P1 | 后端/AI | 修复消费者，不重写业务 |
| Schema 拒收 | 新 release 后出现或突增 | P1 | AI/数据 | 阻断破坏性生产者 |
| 备份失败 | 任一计划备份失败 | P0 | 后端 | 修复并补跑，阻断发布 |
| 磁盘容量 | >80% warn；>90% critical | P2/P0 | 后端 | 扩容/清理可删除数据 |
| 容器重启 | 10 分钟 >3 次 | P1 | 服务 owner | 查看 OOM/健康失败 |

阈值是 MVP 初始候选，Staging 基线测试后可调整；调整需保留原因和版本，不能静默放宽发布 Gate。

## 9. Dashboard

### 9.1 Release Overview

当前 release、请求量、5xx、P50/P95、容器重启、MySQL/Redis/MinIO、最近发布注释。

### 9.2 AI Operations

队列深度/年龄、Task 状态、Worker、Provider 成功率/时延/Token、重试/取消/stale/质量阻断。

### 9.3 Data Reliability

Outbox age、事件接收/拒收/重复、traceability ratio、数据质量 Issue、Metric Job。

### 9.4 Storage and Recovery

MySQL/MinIO/宿主机容量、备份最近成功、备份时长、恢复演练结果。

### 9.5 Security

登录失败、Refresh 重放、权限拒绝、下载签发、Provider 配置变更、Secret/漏洞扫描结果摘要。

每个 Dashboard 支持从聚合图跳到对应 service/release/trace 的 Loki 查询，但不得把敏感字段拼入 URL。

## 10. 保留与轮转

候选默认：

- 容器本地日志：按大小轮转，最多保留 3～7 天缓冲。
- Loki：14 天；容量不足时先删除最旧运行日志，不删除审计/业务事实。
- Prometheus：30 天或按容量上限。
- 告警配置、Dashboard 和 Recording Rule 进入 Git。
- 审计、事件、AI 追溯遵循数据库保留策略，不按 Loki TTL 删除。

生产前根据测试增长率、磁盘和合规要求评审实际值。

## 11. 告警路由与响应

| 范围 | 第一响应 | 第二响应 |
|---|---|---|
| Web/前端错误 | 前端 | 后端 |
| Business API/MySQL/File/Deploy | 后端 | AI/数据 |
| AI API/Worker/Provider | AI/数据 | 后端 |
| Event/Data Quality/Monitoring | AI/数据 | 后端 |
| P0 数据/安全/发布 | 三人同时 + 项目负责人 | 停止发布/写入 |

告警消息包含 environment、service、release、时间窗、指标值、Dashboard/Runbook 链接，不包含正文或 Secret。

## 12. 故障排查顺序

1. 确认环境、release、告警时间窗和用户影响。
2. 检查健康、依赖与近期发布。
3. 用 trace/command/task ID 关联 Business API、AI API、Worker、Outbox 和 MySQL 审计。
4. 判断是业务拒绝、可恢复依赖失败、数据一致性风险还是监控自身故障。
5. 先执行已定义降级：停止新 AI/上传/写入，而不是显示虚假成功。
6. 记录时间线、缓解、根因、影响事实和补偿/修复。

## 13. 测试与验收

- 单元测试验证日志字段、去敏和错误映射。
- 集成测试验证 trace/command/task 跨 HTTP、Celery、Outbox 传播。
- 注入 Provider、Redis、MinIO、MySQL 和消费者故障，验证指标、告警与降级。
- 生成 Secret/Prompt/签名 URL 测试样本，确认日志、指标和错误响应无泄漏。
- 验证正式结果追溯完整率 100%，核心事件必填完整率 ≥99%。
- 验证备份失败、磁盘 >80%、Worker 丢失、Outbox 积压能触发并正确路由。
- 验证 Loki/Prometheus 自身容量受控且不挤占 MySQL/MinIO 恢复空间。

本文已于 2026-07-29 通过用户确认，构成当前有效 V1.0 日志与监控设计基线。告警阈值可依据 Staging 证据版本化调整，但追溯完整、Secret/正文不泄漏、备份失败和数据一致性风险等硬门禁不得放宽。
