# 部署方案

> 文档状态：当前有效
> 基线版本：V1.0
> 生效日期：2026-07-29
> 建立日期：2026-07-29
> 范围：Local、CI、Staging、生产候选拓扑、发布、备份与恢复

## 1. 部署结论

MVP 使用可替换的容器化单服务器拓扑。Docker Compose 是编排基线，不绑定云厂商、服务器型号或托管产品；生产服务器规格需在 MVP 性能与稳定性测试后另行评审。

CloudBase 只在 MVP 核心闭环完成后作为集成测试阶段云端部署 PoC 候选，不作为生产技术基线，不允许使用其专有能力改变业务接口、数据库模型、S3 适配、Redis 语义或服务边界。

## 2. 环境矩阵

| 环境 | 目的 | 数据 | Provider | 可公开入口 |
|---|---|---|---|---|
| Local | 单人开发与模块联调 | 独立本地卷/可重置样例 | 默认 Stub，可显式启用测试连接 | localhost Web/API |
| CI | 构建、单元、契约、迁移、集成 | 临时容器，无持久业务数据 | 仅 Stub | 无 |
| Staging | RC 验证、E2E、性能、恢复演练 | 隔离 DB/桶/Redis Keyspace | DeepSeek 测试 Profile | 受限 HTTPS |
| Production Candidate | MVP 候选运行 | 持久卷、备份、审计 | 已批准 Profile | HTTPS Web/API |

不同环境必须使用独立 Secret、数据库、桶、Redis 前缀和 Provider Profile；禁止把 staging 数据复制为生产事实。

## 3. Compose 服务

| 服务 | 进程 | 对外端口 | 持久化 | 健康检查 |
|---|---|---|---|---|
| reverse-proxy | TLS/路由/限流 | 80/443 | 证书/配置 | 配置加载、HTTPS |
| web | Next.js Node server | 仅内部 | 无业务卷 | `/healthz` |
| business-api | FastAPI | 仅内部 | 无本地业务卷 | `/health/live`、`/health/ready` |
| ai-api | FastAPI internal | 不公开 | 无 | `/internal/v1/health/*` |
| ai-worker | Celery Worker | 不公开 | 无 | Worker heartbeat |
| mysql | MySQL 8.4 | 不公开 | `mysql-data` | ping + 最小查询 |
| redis | Redis | 不公开 | `redis-data` | ping、内存、持久化 |
| minio | S3 compatible | 仅签名对象路径经代理 | `object-data` | live/ready |
| prometheus | metrics | 管理网络 | `metrics-data` | ready |
| loki | logs | 管理网络 | `logs-data` | ready |
| alertmanager | alerts | 管理网络 | 配置 | ready |
| grafana | dashboard | 管理员受限入口 | `grafana-data` | health |

Qdrant 不进入 Sprint 0～5 Compose；Sprint 6 通过独立 Profile 加入。

## 4. 网络与暴露

建议网络：

- `edge_net`：reverse-proxy、web、business-api。
- `app_net`：business-api、ai-api、ai-worker。
- `data_net`：business-api/ai 服务与 MySQL、Redis、MinIO。
- `monitor_net`：采集端与 Prometheus/Loki/Alertmanager/Grafana。

规则：

- 只有 reverse-proxy 绑定宿主机 80/443。
- Grafana 仅允许管理员 VPN、内网或额外认证入口访问。
- AI API、MySQL、Redis、MinIO Console、Prometheus 和 Loki 不绑定公网地址。
- 反向代理只转发签名对象数据路径，不公开桶枚举或 MinIO 管理 API。
- 容器使用非 root 用户、只读根文件系统（需写目录单独挂载）和最小 Linux Capability。

## 5. 配置与 Secret

### 5.1 配置分级

| 类型 | 示例 | 保存位置 |
|---|---|---|
| 非敏感运行配置 | 环境名、日志级别、功能旗标默认值 | 环境变量模板/版本化配置 |
| Secret 引用 | DB 密码、JWT 密钥、Provider Key、S3 Secret | 部署 Secret 文件或 Secret Manager |
| 业务可版本配置 | Provider Profile、模型目录、Prompt 当前版本 | MySQL 受控版本表 |
| 构建期公开配置 | Web 发布版本、公开 API 同源路径 | 构建参数；严禁 Secret |

- 仓库只提交 `.env.example`，不提交真实值。
- `NEXT_PUBLIC_*` 视为公开信息。
- Secret 值不得进入普通 JSON、日志、事件、错误响应、镜像层或备份清单。
- Secret 轮换必须支持新旧短暂并存和会话/服务令牌逐步失效。

## 6. 镜像与版本

- Node、Python、系统包和服务镜像固定到明确版本/摘要，不使用 `latest`。
- Web、Business API、AI API/Worker 使用同一 `product_release` 标识，但可独立镜像。
- AI API 与 Worker 使用同一代码镜像、不同启动命令，避免运行版本漂移。
- 镜像构建采用多阶段构建、锁文件安装、非 root 运行和 SBOM/漏洞扫描。
- 发布候选记录 Git commit、镜像 digest、迁移版本、OpenAPI/事件 Schema 版本和 Design Token hash。

## 7. 启动与依赖

启动顺序：

1. MySQL、Redis、MinIO。
2. 一次性迁移 Job 执行预检和 Alembic upgrade。
3. Business API、AI API、Worker。
4. Web。
5. reverse-proxy。
6. Prometheus、Loki、Alertmanager、Grafana。

`depends_on` 不能代替 Readiness；应用启动必须设置有限重试和明确失败。迁移只能由单独 Job 执行，Web/API/Worker 不在并行启动时自行迁移。

## 8. 健康检查

| 检查 | 含义 | 失败动作 |
|---|---|---|
| Liveness | 进程事件循环/主线程存活 | 重启单容器 |
| Readiness | 能否安全接收该类请求 | 从反向代理摘除 |
| Dependency | MySQL/Redis/MinIO/Provider 状态 | 降级并告警，不统一重启全部服务 |
| Migration | 当前 Schema 是否兼容应用 | 阻止新版本启动 |

Business API 在 Redis/AI 故障时仍可 Ready 处理非 AI CRUD；MinIO 故障时禁止新上传但保留无文件依赖业务；MySQL 故障时只提供维护/健康页。

## 9. 发布流程

1. 冻结 RC：代码、契约、迁移、镜像和已知限制。
2. 运行单元、契约、迁移、E2E、性能、安全和 Secret Gate。
3. 备份 MySQL、对象存储元数据/对象清单和部署配置，验证备份可读。
4. Staging 从上一版本执行迁移并运行 T01～T07、故障降级和恢复演练。
5. 生产候选进入维护窗口；验证磁盘、版本、锁风险、备份时间和回滚条件。
6. 执行一次性迁移 Job。
7. 部署 Business API/AI API/Worker，再部署 Web；最后切换代理。
8. 运行健康、身份、项目、文件、AI Stub/受控 Provider 和关键写入 smoke。
9. 观察至少一个预设窗口的错误率、P95、队列、Outbox、事件拒收、磁盘和备份状态。
10. Gate 通过结束维护；失败进入回滚或前向修复。

## 10. 回滚与数据恢复

### 10.1 应用回滚

- 保留上一稳定镜像和 Compose 配置。
- 只有数据库向后兼容时才允许直接回滚应用。
- 不通过删除新业务事实实现回滚；需要时关闭新功能旗标并运行前向修复。

### 10.2 数据恢复

- MySQL 每日全量备份；生产条件允许时增加 binlog 以缩小实际 RPO。
- 对象存储每日备份或版本化复制；备份包含对象清单和 SHA-256 抽检。
- Redis 不作为事实恢复源；恢复后从 MySQL 重建进度/缓存，未确认任务进入可解释恢复或失败。
- 目标：RPO 24 小时、RTO 4 小时；上线前必须完成一次隔离恢复演练。

### 10.3 迁移失败

- 迁移前检查 Schema 版本、剩余空间、预计锁和备份。
- DDL 失败立即停止新镜像启动；优先前向修复兼容结构。
- 若必须恢复备份，先冻结所有写入，避免旧库与新对象产生分叉。

## 11. 容量与资源候选

生产最终规格不在本阶段冻结。Sprint 0 先建立资源预算和测量：

- Web/API CPU、内存、连接池和容器重启。
- Worker 并发、队列等待、单任务内存与 Provider 限流。
- MySQL 数据/索引增长、连接、慢查询和备份时长。
- Redis 内存、eviction、持久化状态。
- MinIO 容量、对象数量、失败率和备份窗口。
- Loki/Prometheus 日志与指标增长。

MVP 性能基线以 20 个并发活跃用户、50MB 文件和现有 API/SSE 门槛验证，结果作为生产服务器评审输入。

## 12. CloudBase PoC 隔离规则

PoC 开始条件：

- Sprint 0～5 核心闭环已在本地/标准 staging 通过。
- 容器镜像、配置、数据库迁移和 S3/Redis 适配均可独立运行。
- PoC 有单独数据、Secret、域名和成本上限。

PoC 验证：

- 容器/运行时兼容、网络与 TLS、MySQL/Redis/S3 替换可行性。
- SSE、50MB 上传、Worker 长任务、备份恢复与监控可用性。
- 与标准 staging 的行为、错误和性能差异。

PoC 不得：

- 把专有云函数、专有数据库字段或专有存储 URL 写入业务契约。
- 使用 PoC 成功替代生产安全、容量、RPO/RTO 或合规评审。
- 自动升级为生产技术基线。

## 13. 部署责任

| 事项 | DRI | Reviewer/配合 |
|---|---|---|
| Compose、代理、TLS、发布/回滚 | 后端 | 前端、AI/数据 |
| Web 镜像与健康 | 前端 | 后端 |
| AI API/Worker 镜像与队列参数 | AI/数据 | 后端 |
| MySQL 迁移 | 后端 | AI/数据 |
| 备份恢复 | 后端 | AI/数据验证数据完整性 |
| 监控与告警 | AI/数据 | 各服务 owner |
| 最终生产服务器评审 | 用户/项目负责人 | 三名开发人员提供测试证据 |

## 14. 验收条件

- 干净环境可按文档顺序启动全部 MVP 服务。
- 内部数据端口不暴露公网，签名对象请求不授予桶级权限。
- 配置、Secret、镜像、迁移和发布版本可追溯。
- Staging 完成升级、T01～T07、故障和恢复演练。
- RPO/RTO、备份失败告警和旧镜像回滚有可复现证据。
- CloudBase 与生产服务器方案保持候选/待评审状态。
