# 项目一致性检查报告

> 检查日期：2026-07-27  
> 范围：当前工作区 15 份 Word 文档，其中 13 份有效、2 份 0 字节。  
> 原则：本报告只提出问题与建议，不修改任何既有设计。

## 1. 总体结论

产品方向、主业务闭环、七层数据库、AI 动态上下文和技术架构在各文档中总体一致，没有发现需要推翻整体方案的根本冲突。问题主要集中在同一设计经过多轮演进后，旧名称、旧关系和新口径并存，且缺少明确的“领域权威文档”和变更记录。

## 2. 高优先级问题

### C-01 Issue、Bug、Optimization 建模口径不一致

现象：草稿4一处描述 `Issue` 分类为 Bug/Optimization，另一处又给出 `Test Record 1:N Bug`；草稿6/7采用 `issue` 主表 + `bug`/`optimization` 扩展表。部分总览又把 Issue、Bug、Optimization 并列挂在 Project Version 下。

风险：业务归属、外键、API 路径、状态流转和查询统计会产生不同实现。

建议：后续确认唯一模型，例如“Issue 为统一主对象，Bug/Optimization 为互斥或可组合扩展”，并明确 Issue 是否必须属于 Test Record、Optimization 是否可脱离测试产生。当前不直接裁决。

### C-02 Implementation Confirmation 基数冲突

现象：文档同时保留 `Implementation Plan 1:1 Implementation Confirmation` 与 `Project Version 1:N Implementation Confirmation`；物理表 `plan_id UNIQUE` 支持每个 Plan 仅一个 Confirmation，但一个版本可有多个 Plan。

风险：多轮确认、重新确认和实现版本历史无法确定由新记录还是状态更新表达。

建议：明确 Confirmation 是“最终确认对象”还是“确认批次/轮次”，再决定 1:1、1:N 及历史表设计。

### C-03 版本切换/回滚 API 与版本原则冲突

现象：API 提供 `POST /project/version/switch` 并说明用于回滚；数据库原则明确回滚不覆盖历史，应基于旧版本创建新版本。

风险：实现可能把“查看/切换当前版本”和“业务回滚”混为一谈。

建议：区分只读上下文切换、设置当前工作版本、基于历史创建新版本三种语义，并为回滚采用显式派生动作。

### C-04 数据库概念表与物理表数量不一致

现象：草稿6列出 42 张表，包含 `bug_history`；草稿7编号为 41 张物理表，未创建 `bug_history`。草稿4实体清单还出现 `Version Relation`、`Requirement PRD Relation`、`Experience Checklist Relation` 等未落地对象。

风险：迁移脚本、ORM 模型、审计需求和开发任务拆分无法建立稳定基线。

建议：在 Development Planning 前形成唯一的数据字典与 ER 基线，逐项标注“实体、关系表、逻辑概念、暂缓”。

### C-05 项目阶段枚举不统一

现象：草稿2阶段为需求分析、PRD设计、流程设计、设计评审、实现方案、产品验证、优化迭代；完整主流程又包含实现确认，Project Version 生命周期使用设计中、开发中、验证中等更粗粒度状态。

风险：Project.current_stage、Project Version.status、页面导航和 Agent 任务路由可能混用。

建议：分离“项目版本生命周期状态”“工作流节点”“最近访问模块”三套概念，并建立映射表。

## 3. 中优先级问题

### C-06 模块命名与导航归属不统一

现象：文档使用数据中心、知识中心、知识资产中心、AI 能力中心等不同称呼；有时 Skill/Template 属于数据中心，有时属于知识中心或独立 AI 能力中心。

建议：在 Interaction Design 开始前确定一级导航名称和后台领域名称，允许 UI 名称与技术领域名不同，但需建立映射。

### C-07 开发交接文档文件名与正文版本不一致

现象：文件名为 `开发交接文档_V1.1.docx`，正文标题和结尾均写 V1.0。

建议：后续确认真实版本号及变更记录；未确认前引用时同时注明文件名与正文版本差异。

### C-08 Flow 关系口径不一致

现象：草稿4一处定义 `PRD 0:N Flow`，另一处定义 `Project Version 0:N Flow`；物理表只含 `prd_id NOT NULL`。

建议：明确 Flow 是否必须归属 PRD，是否存在跨 PRD/版本级 Flow；据此决定外键和 API。

### C-09 Test Record 归属口径不一致

现象：逻辑设计同时出现 `Implementation Confirmation 1:N Test Record` 与 `Project Version 1:N Test Record`；物理表只含 confirmation_id。

建议：确认直接归属与派生归属，避免重复外键或无法查询版本下全部测试。

### C-10 Context Strategy 版本绑定不足

现象：Context Strategy 设计绑定 `skill_id`，而 Prompt 明确绑定 `skill_version_id`；不同 Skill 版本可能需要不同上下文规则。

建议：评估是否绑定 Skill Version，或通过策略版本/生效区间支持追溯。

### C-11 Checklist 版本原则未落地

现象：生命周期设计要求重要修改生成新版本，但字段和物理表没有 `checklist_version`。

建议：明确采用独立版本表、不可变记录替换，或操作审计即可满足要求。

### C-12 模型实体命名不统一

现象：逻辑文档使用 Model、Model Config；物理表仅 `model_config`，AI Call Record 字段叫 `model_id`。

建议：统一“平台模型目录”与“用户凭证/模型配置”的边界，并避免把 API Key 与模型元数据混为一表。

### C-13 API 风格与路径语义不统一

现象：API 使用 `/project/create`、`/prd/update`、`/review/submit` 等动作式路径，同时资源获取使用 `/project/{id}`；AI 接口既有领域接口 `/ai/prd/generate`，又有通用 `/agent/run`。

建议：后续选择统一资源风格，明确领域 AI 接口是否只是通用 Agent 的业务包装层。

### C-14 API 契约缺口

现象：缺少鉴权、租户/所有权校验、分页筛选、幂等键、并发版本、错误码、文件上传协议、异步任务状态、取消/重试、审计字段和时间格式。

建议：在 Development Planning 前补齐字段级 OpenAPI 契约；当前不修改草稿10。

### C-15 数据闭环缺少落地埋点

现象：产品数据闭环列出事件和指标，但独立埋点文档为 0 字节；指标字段与业务/审计表未映射。

建议：在交互与状态机稳定后建立事件字典和指标血缘，避免页面交互未定时过早固化埋点。

## 4. 数据库专项检查

### C-16 外键和删除策略仅有原则、无物理约束

物理表未声明 FOREIGN KEY；核心数据不删除、归档保留的原则也未映射为软删除/状态/归档字段规范。

建议：开发前定义外键采用数据库约束还是应用约束、级联策略、孤儿数据检测和归档规则。

### C-17 索引写法和字段存在缺陷风险

- 多处 `INDEX` 写在 CREATE TABLE 之外，若直接执行并非完整 DDL。
- checklist 的“`INDEX idx_scenario(stage)`”名称与实际列不符，且 scenario_id 未见对应索引。
- project.current_version_id 与 project_version.project_id 形成循环引用，创建和一致性更新需明确事务策略。
- `is_main=true` 的“同版本最多一个”未由 MySQL 约束实现。

建议：将当前文件视为设计草案而非可执行迁移，并在数据库审查阶段生成可运行 DDL 与自动验证。

### C-18 时间、状态和审计字段不一致

部分表缺 `created_time`、`updated_time` 或操作者；状态默认值和枚举大小写混用；`bug_history.time` 与统一 `created_time` 原则不同。

建议：建立公共字段标准和枚举字典，再生成物理模型。

### C-19 多态关系完整性风险

File Relation、Vector Embedding、Context Record、Operation Log 使用 object_type + object_id，灵活但无法由普通外键保证完整性。

建议：定义对象类型注册表、应用层校验、删除/归档同步和定期孤儿检查。

### C-20 敏感配置风险

`user_setting.api_config` 和 `model_config.api_key_config` 使用 JSON，但未说明加密、脱敏、轮换和访问审计。

建议：后续安全设计将密钥放入专用 Secret 管理或加密列，只保存引用/掩码信息。

## 5. 低优先级与文档质量问题

- 多数 DOCX 没有使用 Heading 样式，机器目录、交叉引用和后续知识抽取不稳定。
- 草稿4包含多轮讨论和重复总览，逻辑设计、ER、实体清单与生命周期混在同一文件中，容易出现旧口径残留。
- `产品数据闭环设计.docx` 开头带有生成说明性文字，“埋点文档待补充”未形成正式待办结构。
- 技术栈有 Chroma/Milvus、FastAPI/Node API 等候选表达；开发前需要区分“已确定”与“可选”。
- GPT-5 等模型名属于示例，不应直接作为长期固定配置。

## 6. 重复设计分析

重复主要集中在开发交接文档对草稿1～10的汇总，以及草稿4内部多版 ER/生命周期描述。重复本身有利于交接，但缺少单向引用导致新旧口径并存。

建议建立文档权威层级：领域主责文档保存细节，开发交接文档只汇总稳定结论，PROJECT_MEMORY 只保存长期摘要；变更通过决策记录和版本号同步。此为维护建议，不修改现有文档。

## 7. 建议处理顺序

1. 先确认文档权威层级与术语表。
2. 裁决 C-01～C-05 五项高优先级口径。
3. 在 Interaction Design 中验证页面导航和流程节点。
4. 在 State Machine 阶段统一项目、版本、Review、Confirmation、Issue/Bug 状态。
5. 再冻结 ER/字段、API 契约和埋点映射。
6. 最后进入 Development Planning，禁止直接把当前物理表草稿当迁移脚本执行。

## 8. 检查限制

两份 0 字节文档无法检查。当前环境缺少 LibreOffice，未完成页面渲染；检查基于所有有效 DOCX 的正文、表格、页眉页脚结构化全量读取，因此内容一致性结论有效，但不包含视觉排版质量结论。
