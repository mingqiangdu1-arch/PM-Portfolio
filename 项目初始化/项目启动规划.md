# 项目启动规划

## 1. 当前项目完成情况

已完成产品定位、核心流程、平台模块、业务数据流、数据库逻辑架构与物理表初稿、系统架构、AI Agent、AI 上下文、API 目录、页面功能结构、MVP 分期和数据闭环指标框架。

初始化阶段已建立 `PROJECT_MEMORY.md`、`PROJECT_STATUS.md`、文档索引、现状分析和一致性检查报告。当前没有代码实现，也没有进入交互或 UI 设计。

## 2. 当前阶段目标

当前仍为 Project Initialization。阶段目标是让后续工作有统一知识入口、清晰资料边界、可追踪未决问题和明确禁区。

初始化收口条件：

- 用户确认五份初始化文档可作为后续工作入口。
- 两份 0 字节资料确认是待补文件还是误同步。
- 高优先级一致性问题已决定进入下一阶段前处理方式。
- 用户明确授权进入 Interaction Design。

## 3. 下一阶段目标

下一阶段为 Interaction Design，仅在明确授权后开始。目标应是把现有页面功能结构转化为角色任务、导航、页面状态、关键操作路径和异常反馈，但不得在该阶段提前冻结 UI 视觉或直接编码。

在进入该阶段前，建议确认：

- 一级导航采用“数据中心”还是“知识中心”，AI 能力如何归属。
- 工作流节点、项目版本状态和最近模块的区别。
- 实现确认是单次最终确认还是多轮确认记录。
- Issue、Bug、Optimization 的统一业务口径。
- 已有资料从指定节点进入时的缺失标记与补充入口。

## 4. 推荐执行顺序

### Phase 0：Project Initialization（当前）

审阅初始化输出 → 裁决高优先级口径 → 标记资料缺口 → 确认进入下一阶段。

### Phase 1：Interaction Design

角色任务梳理 → 信息架构 → 端到端关键路径 → 页面状态与操作反馈 → 文件/AI 长任务交互 → 阶段评审。

### Phase 2：State Machine

分别定义 Project、Project Version、Requirement、PRD/Flow、Design Review、Implementation Confirmation、Test Record、Issue/Bug/Optimization、Experience Candidate、Checklist、Skill 的状态机和跨对象触发关系。

### Phase 3：Wireframe

按已确认交互制作低保真线框，验证模块跳转、阶段进入、版本切换、评审循环、AI 任务状态和差异确认。

### Phase 4：UI Design

建立视觉基础、组件状态、响应式规则和关键页面高保真设计；保持与 Wireframe 和状态机一致。

### Phase 5：Development Planning

冻结 MVP 范围 → 数据库审查与 ER 基线 → OpenAPI 字段级契约 → 埋点字典 → 架构决策记录 → 任务拆分 → 测试策略 → 发布计划。

### Phase 6：Development

优先搭建项目/版本主链和审计基础，再实现产品设计核心闭环、AI 最小调用链，随后按 MVP 阶段加入实现确认、验证和知识能力。每个实现必须引用已确认设计。

### Phase 7：Testing

覆盖单元、集成、API 契约、状态机、权限、AI 可追溯、文件处理、数据质量、故障降级和端到端业务流程。

### Phase 8：Iteration

以真实埋点、AI 质量、用户修改和版本效果验证为依据迭代 Prompt、Skill、流程和产品能力。

## 5. 推荐的开发优先级（仅用于后续规划）

1. 基础身份、Project、Project Version、Project Context 与审计框架。
2. Requirement、PRD/PRD Version、Review/Feedback 与基础文件能力。
3. Task Router、Skill、Context Strategy、Prompt Builder、Model Gateway、AI Call/Context Record 的最小闭环。
4. Implementation Plan/Confirmation/Difference Record。
5. Test Record、Issue/Bug/Optimization 与新版本回流。
6. Experience Candidate、Experience、Scenario、Checklist 和混合检索。
7. 数据埋点、指标计算与分析看板。

该优先级不代表当前授权开发。

## 6. 风险点

- 资料风险：两份关键文档为空，MVP 与埋点缺少独立基线。
- 一致性风险：多轮草稿中旧关系与新关系并存，若直接编码会固化错误口径。
- 状态风险：项目阶段、版本状态、流程节点、最近模块混用。
- 数据风险：物理表草稿缺完整外键、约束、索引、归档和敏感配置方案。
- API 风险：动作式接口与资源式接口混用，异步 AI、文件上传、幂等与错误处理未定义。
- AI 风险：上下文策略和 Skill 版本绑定不充分；质量评分、重试阈值和人工确认边界未量化。
- 知识风险：候选、审核、启用、废弃和版本化规则尚未完全映射到物理模型。
- 范围风险：数据中心、知识中心、Skill 管理和分析看板容易提前扩大 MVP。
- 技术风险：候选技术栈尚未全部形成 ADR；个人部署架构与未来扩展需避免过早微服务化。

## 7. 阶段门禁

每阶段开始前：读取 `PROJECT_STATUS.md` 与 `PROJECT_MEMORY.md`，确认授权、输入文档和未决问题。

每阶段结束前：

- 验证产出与领域主责文档一致。
- 更新引用关系、决策记录和 `PROJECT_STATUS.md`。
- 不把未确认建议写成既定事实。
- 若修改 Git 仓库文件，检查变更范围、验证结果和提交条件，取得用户确认后再 Commit；存在远程时再询问 Push。

## 8. 当前建议动作

保持项目在 Project Initialization，先审阅 `项目一致性检查报告.md` 的 C-01～C-05，并确认两份 0 字节文件的处理方式。完成这些确认后，再由用户明确下达 Interaction Design 阶段任务。
